# 部署、迁移与迭代计划

## 第一版部署形态

单台 Linux 主机 / 容器平台运行 HTTPS 代理、Web、scheduler、worker 和 PostgreSQL。数据库和证据目录使用持久卷；数据库不向公网暴露。开发机可继续使用 Windows，通过 Linux 容器验证生产运行方式。

Web、worker 和 scheduler 使用同一个不可变版本标签/镜像摘要；需要浏览器时增加同源码版本的 browser-worker 镜像。普通 worker 不必携带浏览器依赖。镜像、浏览器和 Python 依赖均锁定版本，升级通过测试进入发布流程。

数据库迁移为发布阶段的一次性任务，成功后才启动或切换新服务。应用初始化只加载配置和注册模块，不在 Web import 时建表、导入持仓或启动 scheduler。首位管理员通过独立命令创建，生产缺少密钥或数据库连接配置时启动失败。

建议配置：`DATABASE_URL`、`SESSION_SECRET`、`APP_ENV`、`BUSINESS_TIMEZONE`、`ARTIFACT_STORAGE_PATH`、`WORKER_CONCURRENCY`、`LOG_LEVEL`。来源频率、阈值和适配器配置存数据库并审计。`.env.example` 只放占位符；真实密钥、银行会话、原始账单不进代码仓库和镜像。

## 分阶段实施

| 阶段 | 交付内容 | 完成条件 |
| --- | --- | --- |
| M0：部署与拆分基础 | 修复 Dockerfile 命名和首启初始化；应用工厂；模板/静态文件外移；移除默认生产凭据和真实种子；拆出 scheduler；建立 Git 与 CI | 空数据卷启动、已有卷重启都可用；模块 import 无调度副作用；迁移可重复执行 |
| M1：多用户和数据底座 | PostgreSQL + schema 迁移；产品/账户/交易/持仓分表；权限校验、审计；旧台账迁移工具和核对报告 | 两个用户读写相同产品互不影响，不能访问彼此账户/任务/导出；迁移余额核对一致 |
| M2：多来源采集 | 提取中银适配器；持久队列、租约、重试、分页、原始证据；新增至少一个实际验证通过的其他机构来源；实现 HTML/DOM 适配路径 | 至少两个机构可采集并正确映射产品；API 和页面解析各有契约样本；页面来源未核实时不得宣称自动接入完成 |
| M3：收益跟踪与第一版验收 | 交易重放、日快照、周/月/自定义区间；申赎分红；数据完整性；导入预览与确认；后台任务状态 | 计算用例与越权用例通过；历史修订可重算；用户可查看周期收益及其净值日期 |
| M4：按真实需求扩展 | OCR 自动化、更多银行、私有连接器、TWR/XIRR、关注提醒、独立队列等 | 每项按实际需求独立验收，不把未支持指标混入已支持收益 |

第一版页面识别至少实现 HTML/DOM 路径；若首批目标页面确实只有图片，则把 OCR 和人工复核前移到 M2。多银行自动采集的完成以真实来源验收为准，不能用枚举新增机构代替。当前未知团队规模和部署约束，因此不承诺固定工期。

## 数据迁移与切换步骤

1. 对旧 SQLite 做一致性备份，保存校验 hash；记录产品数、净值数、总份额/成本（按产品与币种）以及重复代码。只读分析可在副本进行。
2. 在 PostgreSQL 创建目标 schema；固定旧数据归属的历史用户和账户，不复制给每个新用户。人工确认无法自动分辨的银行销售渠道、发行机构和份额类别。
3. 迁移产品/来源映射、旧净值和期初持仓；旧主键+迁移批次作为幂等标识。输出拒绝行、冲突行、缺失日期，不静默忽略。
4. 在预发布环境核对每产品净值记录数、最后日期、持仓份额、剩余成本及同一净值下市值；差异须有明确舍入解释或修正。模拟至少一次重复导入，确认无重复记账。
5. 正式切换时短暂进入只读，补做最终一致性备份和迁移；停止旧调度器，再启动新服务与任务进程。初期使用短维护窗口，避免双写复杂度。
6. 切换后验证登录、两用户隔离、快照和新采集；新系统一旦接受新写入，就不能直接切回旧 SQLite 而丢掉新交易。需要导出/重放新增流水，或优先修复新系统。

## CI/CD 流程

建议在选定 Git 托管平台后落实以下流水线；当前目录还不是 Git 仓库，也没有部署目标。

```text
提交/PR
  → 静态检查、单元测试
  → 临时 PostgreSQL 上迁移与集成测试
  → 采集脱敏样本契约测试、收益与授权测试
  → 构建版本镜像并检查依赖
  → 预发布迁移与冒烟测试
  → 生产备份和兼容性检查
  → 单次 schema 迁移
  → 更新 Web / worker / scheduler
  → 就绪检查、登录及采集冒烟
  → 发布记录与观测
```

真实银行网络测试只作为受控定时探测，不把外站波动变成每次 PR 的必然阻塞条件。PR 使用冻结样本测试解析和数据口径；生产接入验收仍要真实验证来源。

版本发布记录包含源码版本、镜像摘要、schema 版本、parser 版本、formula 版本、迁移输出和备份引用。生产发布由受保护环境或指定发布流程触发；先部署预发布验证，再推广同一镜像。

## 兼容升级和回滚

- 使用 expand → migrate → contract：先加兼容字段/表，再回填和切换读写；确认所有旧进程退出并经过观察后，后续版本才删除旧字段。
- 新增必填字段先允许空值，回填校验后再加约束。大数据回填分批、可续跑，避免长事务阻塞应用。
- 任务 payload 显式带版本；升级期间 worker 能读取当前和上一版本，或先停止领取、排空旧任务再切换。无法识别的版本不得默默执行。
- worker 收到停止信号后停止领取新任务，等待有界时间完成；未完成任务靠租约恢复。scheduler 即使短时双实例也依靠唯一任务键去重。
- 应用故障先回滚兼容的上一镜像；已执行破坏性数据库迁移不能靠回滚镜像解决，应先停写、评估备份恢复或前向修复。恢复备份会丢失备份后写入，必须有明确的数据恢复流程。
- parser 故障先禁用对应来源、隔离错误候选，再修复解析器并重放证据；错误净值已生效时发布新修订并重算相关快照。不能只回滚代码而留下错误收益。

## 健康检查、告警与备份

`/health/live` 仅判断进程活性；`/health/ready` 检查数据库连接和 schema 兼容性。外部银行暂时不可用不应让整个 Web 服务失去就绪状态。scheduler/worker 另有数据库心跳、队列等待时间和任务租约监控。

结构化日志包括 request_id、job_id、source_id、product_id、parser_version 和错误类型。监控采集成功率、各来源净值延迟、队列最老等待时间、OCR 待审数量、重算延迟及数据库容量。不要把用户持仓金额、密码、会话、原始账单内容放进日志。

建议初始告警：连续三次来源采集失败、超过来源配置公布时限仍无净值、队列等待超过 30 分钟、worker 无心跳、快照重算失败；阈值需结合实际银行公布规律调整。汇总只通知状态改变和需要处理的问题，避免每轮重复告警。

第一版可提出 RPO ≤ 24 小时、RTO ≤ 4 小时作为待验收目标：每日加密数据库备份到独立故障域，发布前额外备份，证据文件和数据库引用一致备份；每日备份保留 30 天，月备份保留 12 个月可作为初始策略，最终由数据保留需求确定。每月至少做一次隔离恢复演练，实测恢复时长和账目一致性。若每日新增交易无法容忍 24 小时损失，启用 WAL 归档/PITR 并重新定义目标。

## 第一版验收清单

- 部署：从空库建表和创建管理员成功；升级保留数据；仅有一份有效周期任务；应用重启不重新灌入种子。
- 权限：用户 A 猜测用户 B 的账户、流水、导入文件、任务和导出 ID 时不能读取或修改；公共净值修改仅对授权角色开放。
- 数据源：中银及至少一个其他机构实测通过；代码映射不串产品；分页覆盖目标区间；接口空值与“未支持来源”分开；API、DOM、异常格式有冻结样本。
- 幂等：重复点击同步、任务重复投递、租约过期后重领、账单重复导入均不会重复记账；旧 worker 无法提交过期结果。
- 收益：固定份额、分批买入、部分/全部赎回、现金分红、红利再投、手续费、期初迁移、缺失净值、跨周末、历史补录和净值更正均有已知预期值。
- 一致性：同一版本内日报累计等于对应周/月区间金额；前端展示和导出使用同一服务端公式；舍入只发生在约定位置。
- 可运维：单银行故障不影响其他银行及页面；失败可定位至任务/证据；备份恢复演练通过；上一兼容镜像可回滚。

建议先实施 M0 与 M1，再扩充银行采集。否则新增来源会进一步扩大现有共享持仓、历史收益失真和重复调度的问题。
